## 1. Форматы: что заменил miniSEED, а что осталось

Разобрано и закрыто:

| | Что это | Судьба |
|---|---|---|
| **SDF** | сырая волна датчика | **заменён miniSEED**, бинарный формат удалён |
| **SAF** | признаки анализа (RMS, частота, health) | остался как **модель данных** (CBOR по шине + SQLite) |
| **SHF** | аномалии и их история | остался как **модель данных** |

miniSEED хранит **только волну**. SAF/SHF — это то, что *вычислено* из волны,
в miniSEED такого нет в принципе. Точно так же устроен SeisComp: miniSEED для
волн, `Amplitude/Magnitude/Event` — объекты в БД.

Файловые сериализаторы `SdfFile/SafFile/ShfFile` были мёртвым кодом (никто не
использовал) и **удалены**. Структуры `SdfRecord/SafRecord/ShfRecord` живые.

## 2. Три независимые оси

Их нельзя смешивать — это разные вопросы:

| Ось | Что решает | Варианты |
|---|---|---|
| **Транспорт** | как байты доходят | UART, RS-485, Ethernet/RJ-45, Wi-Fi, LoRa |
| **Формат** | что в байтах | STM32-протокол (CRC-16), miniSEED, SeedLink |
| **Роль узла** | что узел делает | Hub (сбор+форвард) / Центр (master+БД+GUI) |

Сейчас транспорт UART **зашит** в `SerialStreamReceiver`. Нужна абстракция
`Source` (как `RecordStream` для архива, только для живого приёма):

```
tpacq --source serial://COM6?baud=460800    # есть сейчас
tpacq --source rs485://COM3?addr=1..20      # шина, адресный опрос
tpacq --source tcp://0.0.0.0:9000           # датчик по Ethernet/RJ-45
tpacq --source lora://COM4                   # LoRa-шлюз (события)
```

### LoRa — особый случай
Полоса LoRa не тянет 200 Гц × 3 оси. LoRa-датчик должен **считать на краю**
(RMS/health/аномалия) и слать наверх **только сводку**. Это не «ещё один Source»,
а мини-TerraPulse на самом датчике.

## 3. Арифметика, которая диктует архитектуру

> ⚠️ Раздел переписан. Прежняя редакция утверждала «сырьё наверх — никогда» и
> называла 1.2 Гбит/с доказательством невозможности. Это была **ошибка сравнения**:
> 1000 станций SeisComp — это ~3 000 каналов, а «300 Hub × 200 датчиков» —
> 180 000 каналов, в 60 раз больше. SeisComp штатно принимает сырьё с 1000+
> станций в центр, и наша схема должна уметь так же.

### Числа

Все цифры живут в **[ЗАМЕРЫ.md](ЗАМЕРЫ.md)** и здесь намеренно не дублируются —
иначе две копии со временем разойдутся, что уже один раз и произошло.

Кратко, из [§1–2 замеров](ЗАМЕРЫ.md):

- 📏 архив сейчас **5.15 Б/сэмпл** при несжатых 4.00 — то есть **на 29 % больше
  сырых данных**, потому что 512-байтная запись заполняется лишь на ~99 сэмплов
- 🧮 один датчик (3 оси × 200 Гц) — **24.7 кбит/с** в нынешнем виде
- 💭 после заполнения записи ожидается ~6.5 кбит/с, но **это непроверенная
  оценка**, а не факт
- 🧮 1 000 датчиков ≈ 25 Мбит/с сейчас; 10 000 ≈ 247 Мбит/с

### Выводы

1. **Сырьё в центр — режим по умолчанию**, как в SeisComp. До ~10 000 датчиков
   это 65 Мбит/с и не требует никаких ухищрений.
2. **Ограничивает не канал, а хранилище** — и только на десятках тысяч датчиков.
3. **Локальное хранение на Hub + сводка наверх — опция**, а не обязательная
   схема: для тонких каналов (LoRa, сотовая связь), для экстремального масштаба
   и для объектов, где сырьё не нужно постоянно.
4. **Заполнение записи miniSEED — задача с самым высоким отношением пользы к
   цене** во всём этом разделе: одна настройка даёт ~4× по каналу и по диску.

> Прежний вывод «12 000 сообщ/с — tpmaster задохнётся» тоже снят: ZeroMQ
> XSUB/XPUB держит миллионы мелких сообщений в секунду. Реальное узкое место —
> запись в SQLite и отрисовка в GUI, агрегировать нужно ради них.

## 3a. Транспорт сырья: «точка = сообщение» — потолок по масштабу

> ⚠️ Это **частота сообщений**, а не полоса (§3). Полоса на 200 датчиков ~5 Мбит/с —
> пустяк. Проблема в другом: сколько отдельных сообщений в секунду проходит через
> брокер и сколько раз каждое кодируется/декодируется.

📏 **Замер 2026-07-28** (tpmon по `raw.`, 1 симулятор 200 Гц): **~198 сообщ/с на
датчик** — одно CBOR-сообщение на тройку X/Y/Z.

🧮 Проекция:

| Датчиков | raw-сообщ/с (произведено) | × ~5 потребителей (tpproc/tpqc/tpwfparam/tpslinkserver/GUI) |
|---|---|---|
| 2 (текущее демо) | ~400 | ~2 000 — тривиально |
| 50 | ~10 000 | ~50 000 |
| 200 | ~40 000 | **~200 000 доставок/с** |

**Уточнение к снятому выводу выше.** Сам ZeroMQ-транспорт столько тянет. Дорого не
это, а **обработка каждого сообщения**: CBOR-кодирование в tpacq и
CBOR-декодирование + сборка QVariantMap + диспетч в *каждом* потребителе. При
40 000 сообщ/с × 5 это уже заметный CPU только на упаковку/распаковку.

### Целевая схема (после дедлайна) — record/ring backbone, как в SeisComp

Сейчас:
```
tpacq/tpslink → raw.* (точка=сообщение) через tpmaster → tpproc/tpqc/tpwfparam/tpslinkserver/GUI
```
Ближе к SeisComp:
```
tpacq/tpslink → miniSEED record / ring / archive → потребители через RecordStream
processing    → saf. / shf. / qc. / wfp. / evt. через tpmaster (только результаты)
GUI           → живое/разбор через RecordStream + статус/события через tpmaster
```

Смысл: **сырьё течёт записями (пачки сэмплов), а не точками**, и по своему каналу
(record/ring/SeedLink), а брокер несёт только вычисленное. Дешёвый промежуточный
шаг — **батчинг**: слать N сэмплов одним сообщением (частота падает в N раз без
смены архитектуры).

**Оценка порога:** нынешняя схема нормальна примерно **до 20–50 датчиков**; на
сотнях нужен record-backbone. Это **не ошибка, а потолок**. Разбор подтверждён
пользователем через сравнение с SeisComp (2026-07-28).

## 4. Передача Hub → центр: два канала

| Канал | Что передаёт | Когда | Статус |
|---|---|---|---|
| **Сырьё** (SeedLink) | волны | **постоянно — режим по умолчанию** | ⚠️ нужен **SeedLink-сервер на Hub** |
| **Сводка** (`tprelay`) | события, аномалии, статус, качество | постоянно | ✅ готово |
| **Волна по запросу** (`tpws`) | окно вокруг события | когда сырьё не гоняем постоянно | ✅ эндпоинт есть |

Сырьё и сводка — **не альтернативы**, а два параллельных канала: SeedLink несёт
волны, `tprelay` несёт вычисленное (события, качество, параметры). Так же устроен
SeisComp: `seedlink` отдаёт waveform, messaging несёт объекты.

Отключить постоянное сырьё имеет смысл только при тонком канале или на десятках
тысяч датчиков — тогда работает третий вариант, волна по запросу.

Сейчас `tpslink` — **только клиент** (умеет принимать). Чтобы Hub *отдавал*
волны по SeedLink, нужен сервер (как `seedlink` в SeisComp).

### Рекомендуемая схема
```
Hub (здание):
  • собирает N датчиков (UART / RS-485 / Ethernet)
  • СЧИТАЕТ ЛОКАЛЬНО (tpproc, tpqc, tpwfparam)
  • хранит полное сырьё в miniSEED-архиве у себя
  • наверх: сырьё по SeedLink + вычисленное через tprelay
        ↓
Центр:
  • видит все Hub, все здания, здоровье и события в реальном времени
  • держит собственный архив волн (как SeisComp)
  • локальный архив Hub остаётся страховкой на случай обрыва связи
```
Локальный расчёт на Hub нужен **не только ради экономии канала**: он даёт
живучесть. Оборвалась связь с центром — здание продолжает само себя оценивать и
поднимет тревогу локально, а накопленное уйдёт наверх при восстановлении
(store-and-forward уже работает).

**Режим «тонкий канал»** (сырьё наверх не идёт) включается конфигом там, где это
оправдано, и остаётся полноценным вариантом — но это настройка, а не архитектура.

## 5. Иерархия узлов

При сотнях Hub «звезда» не работает — нужна многоуровневая схема:

```
Hub (здание, ~200 датчиков)
   ↓ сводка по зданию
Региональный TerraPulse (город, ~50 Hub)
   ↓ сводка по региону
Национальный центр
```

`tprelay` умеет пересылать группы, но **на каждом уровне данные должны
схлопываться**, а не просто пересылаться. Режим агрегации — к реализации.

## 6. Адресация — ключевое открытое решение

При 100k датчиков плоские `station/object/sensor` не годятся: два Hub
независимо возьмут `object=1, sensor=1` и в центре сольются.

**Предложение — взять FDSN-схему** (она и так внутри miniSEED):

| Уровень | Смысл |
|---|---|
| `network` | регион / оператор (напр. `UZ`, `TAS`) |
| `station` | здание / объект — **глобально уникальный код** |
| `location` | этаж / позиция |
| `channel` | ось (`HNX` / `HNY` / `HNZ`) |

**Плюс:** source id в архиве сразу глобально уникален и совместим с SeedLink и
любым сейсмологическим софтом.

> ⚠️ Это решение **блокирует** топики, архив, инвентарь и GUI.
> Менять его после развёртывания Hub — очень дорого.

## 7. Настройка на масштабе: три уровня

Никто не настраивает сотни датчиков поштучно.

| Уровень | Что | Где живёт | Объём |
|---|---|---|---|
| **1. Инвентарь** | что где физически стоит | центр (источник правды) | десятки тысяч |
| **2. Профили** | как анализировать | центр, раздаётся | **3–10 штук** |
| **3. Узел** | роль, адреса, порты | локально на Hub | ~5 параметров |

- **Инвентарь** раздаётся нотификаторами `inv.` — механизм есть; нужно слать
  **только изменения**, а не файл целиком.
- **Профили** (`profile_bridge`, `profile_highrise`) + привязки `etc/key/…` —
  механизм есть и проверен (`terrapulse update-config` валидирует).
- **Конфиг узла** — минимальный, шаблонный.

### Zero-touch provisioning (обязателен на масштабе)
```
Hub включили → звонит в центр (серийник/сертификат)
             → центр выдаёт station id + профили + его часть инвентаря
             → Hub стартует сам

Датчик воткнули → Hub видит новый адрес на шине → регистрирует автоматически
```
Автоподхват датчика — это «sensor auto-registration on first data» из SeedLink4
(зафиксировано в разборе каталога).

### Раздача конфига
Группа **`cfg.` уже зарезервирована в шине, но не используется** — это её
назначение: раздавать профили и привязки из центра как данные.

## 8. GUI на масштабе

При 100k датчиков список не работает. Нужно **дерево**:
`страна → регион → здание → датчик`, цвет узла = худший потомок,
разворачиваешь только проблемное.

Это меняет GUI **по сути**, а не только по оформлению (внешний вид тоже
планируется переделать; за референс компоновки — scolv / SHARD).
