## Автомат состояний: две фазы

Взаимодействие клиент↔сервер жёстко делится на две фазы:

1. **Текстовая фаза конфигурации** — строки ASCII, оканчиваются `\r\n`, запрос-ответ.
2. **Бинарная фаза реального времени** — непрерывный поток 520-байтных пакетов.

Переход из первой во вторую — по команде `DATA`. После неё сервер **больше не
принимает текст**, клиент **больше ничего не пишет** в сокет.

---

## Фаза 1 — текстовый хэндшейк (порт 18000)

| Шаг | Клиент → | Сервер ← |
|---|---|---|
| Приветствие | `HELLO\r\n` | 2 строки: «имя+версия сервера», затем «организация» (или `SEEDLINK`) |
| Станция | `STATION <STA> <NET>\r\n` | `OK\r\n` если станция есть в кольцевом буфере, иначе `ERROR\r\n` |
| Каналы | `SELECT <канал>\r\n`, напр. `SELECT HN*\r\n` | `OK\r\n` |
| (повтор `STATION`→`SELECT` для нескольких станций — multi-station) | | |
| Запуск | `DATA\r\n` (реальное время) или `FETCH` (архив) | `OK\r\n` → бинарная фаза |

- **Uni-station**: `SELECT`/`DATA` без `STATION` — один поток по умолчанию.
- **Multi-station**: `STATION … SELECT …` повторяется, завершается `END`.
- `CAT` — сервер отдаёт список станций.

Коды каналов по FDSN: сеть / станция / локация / канал. Для акселерометра канал
начинается на `HN` (`HNZ` верх, `HNN` север, `HNE` восток); у нас ось X/Y/Z →
`HNX/HNY/HNZ`. Это ровно то, что строит наш `StreamId` (этап 1.3).

## Фаза 2 — бинарный пакет: ровно 520 байт

```
+--------------------+----------------------------------------+
|  SLxxxxxx (8 байт) |        MiniSEED-запись (512 байт)      |
+--------------------+----------------------------------------+
|<----------------------- 520 байт ----------------------->|
```

- **8 байт заголовка**: `'S' 'L'` + **6 символов порядкового номера** пакета,
  затем формируется полная 520-байтная рамка. Номер нужен клиенту, чтобы после
  обрыва возобновиться **без потери данных**.
- **512 байт тела**: чистая стандартная miniSEED-запись — сжатые отсчёты, точное
  время первой точки, метаданные канала.

## Архитектура сервера: кольцевой буфер + курсор на клиента

```
              tpslinkserver (отдельный процесс, решение §16)
             +-----------------------------+
             |   Глобальный Ring Buffer     |
             +-----------------------------+
               ^ push 512B            | pop 512B (свой курсор на клиента)
               |                      v
   raw. с шины ──> упаковка miniSEED   QTcpServer :18000 ──520B──> внешний клиент
   (tpacq)        (tp::mseed::encode)                              (tpslink / ObsPy)
```

Поведение сервера:
- На каждого клиента — свой `QTcpSocket` и свой **указатель чтения** в общий
  кольцевой буфер.
- Приём (`tpacq`) кладёт новую miniSEED-запись в голову буфера; сервер
  просыпается по сигналу, дописывает 8-байтный заголовок → 520 байт → `write()`.
- **Медленного клиента сервер не ждёт** — копит в буфере.
- Клиент **отстал так, что буфер перезаписался** → сервер принудительно рвёт
  связь (защита памяти от зависания).

Поведение клиента (у нас уже так):
- После `DATA` парсер в режиме «бинарный накопитель».
- В `readyRead` не читает построчно: ждёт `bytesAvailable() >= 520`.
- Отрезает 8 байт (номер — в историю для возобновления), 512 байт miniSEED — в
  локальный буфер/архив.

## Точки, которые сверить с опубликованной спецификацией при реализации

Обзор выше концептуально верен; ниже — места точного формата на проводе, которые
надо зафиксировать по спецификации, когда будем писать байты (этап 5):

1. **Номер последовательности — 6 шестнадцатеричных цифр** (24-битный, `0..FFFFFF`
   с переполнением), не десятичный. Наш клиент читает 6 символов заголовка —
   согласовать основание.
2. **Возобновление — это `DATA <seq>` / `FETCH <seq>`** в классическом SeedLink v3
   (номер в hex после команды), а не отдельное ключевое слово `RESUME`. Проверить
   и реализовать именно `DATA <seq>` — с этим уже связан этап 3.2 (сейчас клиент
   номер выбрасывает).
3. **Ответ об ошибке** — уточнить `ERROR\r\n` vs `ERR\r\n` по спецификации.
4. **`END`** завершает multi-station хэндшейк — заложить в автомат сервера.

Эти четыре — единственное, что осталось «сверить»; всё остальное описания
принимается как требование к `tpslinkserver`.

## Состояние реализации (2026-07-26)

| Что | Статус |
|---|---|
| Кольцевой буфер + обрамление 520 Б + контракт Ok/TooOld/Future | ✅ `SeedLinkRing`, юнит-тест |
| TCP-сервер + хэндшейк `HELLO/STATION/SELECT/DATA/END/BYE` | ✅ `tpslinkserver`, петля проверена |
| Реальное время из кольца по курсору на клиента | ✅ |
| Возобновление `DATA <seq>` (сервер) + переподключение (клиент) | ✅ проверено на перезапуске сервера |
| SELECT-селекторы каналов (`HNZ`, `HN?`, `!`-негатив) | ✅ фильтр по location+channel, проверено |
| Multi-station в одном сокете | ⬜ нужны по-станционные буферы (структурная работа) |
| Номера hex (сверить основание), `RESUME` vs `DATA <seq>`, `ERROR`/`ERR` | ⬜ 4 точки выше |

**Оговорка по возобновлению без потерь.** Полный бэкфилл после обрыва работает,
пока **сервер жив** (кольцо в памяти держит последние N пакетов — контракт под
юнит-тестом). Через **перезапуск сервера** номера сбрасываются: клиент просит
старый seq, сервер честно отвечает real-time вместо зависания. Непрерывность
номеров через перезапуск требует их хранения на диске (как в SeisComp) — это
отдельная будущая работа, не блокер для передачи волн между живыми узлами.
